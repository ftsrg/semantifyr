# How the Language Works

An OXSTS model, written by hand or translated from another language by a [frontend](../index.md), describes a system by its structure: classes whose instances contain instances of other classes, and transitions that call other transitions. What a [backend](/category/backends) checks is a transition system: variables, an initial transition, one transition the system takes again and again, and a property over the variables. The compiler turns the one into the other, for one verification case at a time, in three phases.

<PhaseChain />

1. [Instantiation](instantiation.mdx) builds the instance tree: from the case down, an instance for every containment of multiplicity one.
2. [Inlining](inlining.mdx) replaces every call by its body, as the class of the instance it is called on defines it, until the case is one transition over instance paths such as `root.left.on`.
3. [Flattening](flattening.mdx) turns every variable of every instance into one variable of the model and leaves no instance: the transition system.

The three pages step through what the compiler writes for this one model. Every model they show is the compiler's own output, written when the site is built and shown whole, except the model itself, `room.oxsts` below, where instantiation's walk starts; only the instance tree is drawn by hand, since the compiler keeps it in memory.

<CodeBlock language="oxsts" title="room.oxsts">{room}</CodeBlock>

The command line writes the same files for any model: `semantifyr compile --artifacts=debug` keeps the model after each phase and after every single step in the case's directory, as [the command line's page](../cli/index.mdx) describes.
