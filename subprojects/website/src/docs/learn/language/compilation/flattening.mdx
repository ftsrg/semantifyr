# Flattening

Flattening is the third and last phase of the compilation. It starts from the model [inlining](inlining.mdx) wrote and the instance tree, and leaves a transition system: variables, an `init`, one transition and a property, with no instance left. It rewrites the model seven times, in this order:

1. Every variable of every instance is declared as a variable of the model, named by its path: the `on` of `root.hall.top` is declared as `'$$root$$hall$$top$$on'`. A variable that holds an instance, one whose type is a class or a feature, is typed `Anything` until the last rewrite.
2. Every use of a variable through an instance path is rewritten to that variable of the model.
3. A local variable that holds an instance is typed `Anything` too.
4. A record variable becomes one variable for each field.
5. An array variable becomes one variable for each slot.
6. A `havoc` of a variable that holds an instance becomes a choice over the instances it can hold, and `nothing` where its multiplicity allows it.
7. A variable that holds an instance becomes an `int`, `nothing` becomes `-1`, every instance an expression still names becomes its number, and `contains root` goes. The case's `mapping.json` lists the numbers.

The phase's optimizations then run until none of them changes the model: they simplify expressions and nested operations, remove redundant operations, propagate false assumptions and copies, substitute variables that keep one value, and remove dead stores, dead code and the variables nothing reads.

What the phase writes, `pipeline/flattened.semantifyr`, is what `semantifyr compile` writes as its output and what a [backend](../../backends/index.mdx) receives, each translating it into its own input language.

The compiler writes a frame after each rewrite that changes the model and after each optimization that fires. This model has no local, record, array or `havoc`, so the walk shows the rewrites 1, 2 and 7. The first declares an `on` for each lamp, one `ok` for the fuse both lamps share, which an `assume` in each branch reads, and the hall's `last`, which holds a lamp, typed `Anything`. The second rewrites the transition and the property to these variables, and the lamps named as values, in the guards and the assignments of `last`, keep their paths. The last numbers the instances in the order it meets them, `root.hall.top` `0` and `root.hall.bottom` `1`, makes `last` an `int` that starts at `-1`, and leaves the guards comparing `last` with the numbers: a lamp toggles only when it was not the last to toggle. The optimizations follow: nothing writes the fuse's `ok`, so its reads become `true` and the variable goes, and each `assume(true)` goes.
